## Purpose

Define the deterministic S5 E0 boundary that turns one sealed Plan and its frozen inputs into a protocol-neutral, buildable, smoke-validated, receipt-bound workspace without using an LLM or claiming that task-owned stubs are implemented.

## Requirements

### Requirement: S5 admission validates the complete sealed input before workspace effects
S5 SHALL start only for the E0 instance of a fresh run whose S4 stage is done and whose immutable Plan 1.0.0, active pointer, configuration anchor, frozen Spec/Target/Test Bundle refs, file ledger, and revision ledger all validate. It SHALL recompute Delivery Constraints and the Delivery Blueprint through the same deterministic compiler used by S4, require canonical equality with the sealed Blueprint hash, and run basic plus stage-full Plan lint before creating or modifying the workspace. S5 SHALL NOT trust an `_s4` candidate, a caller-supplied Blueprint, or files that merely exist without the committed S4 Run anchor. (Design 8.0.2: §5.2.1, §6.5, §10.2.1-§10.2.2; pipeline design 2.0.2 §5.4; D1.10; M1-5.)

#### Scenario: Valid E0 input is admitted
- **WHEN** the completed S4 seal, frozen inputs, active pointer, ledgers, recomputed constraints, recomputed Blueprint, and full lint all agree
- **THEN** S5 may construct the rendering view and no input value is taken from the workspace or an LLM

#### Scenario: Blueprint or frozen input drifts
- **WHEN** a frozen input byte, sealed hash, active pointer, or recomputed Blueprint differs from the committed S4 anchors
- **THEN** S5 fails before the first workspace side effect and records the controlled failure rather than materializing from the drifted value

#### Scenario: Publication files exist without an S4 commit
- **WHEN** Plan or ledger files exist but `run.stages.s4=done` and its complete output refs are absent
- **THEN** S5 refuses admission and leaves the workspace absent or unchanged

### Requirement: The S5 rendering view is complete, canonical, and derived without Plan mutation
S5 SHALL derive one canonical rendering view from the sealed Plan, frozen Spec/Target, and recomputed Blueprint without modifying the Plan. It SHALL classify complete C99 export declarations as function, type, or constant; normalize supported function return and parameter declarations; derive each function's `implementation_file` from an explicit binding or the unique intersection of its declared provider task files and Blueprint source/link-source slots; derive `stub_rule=not_implemented`; compute declared-symbol dependencies and cross-header includes from the unique export binding; and bind each executable entry to its Blueprint `entry_file_slot`. It SHALL accept only the finite C99 declaration and type forms in §5.2.1 and SHALL reject an unparsable declaration, undeclared or ambiguous referenced symbol, non-closed type dependency, missing/ambiguous implementation source, missing/duplicate entry point, or extra `main` without guessing from names, suffixes, prose, or protocol identity. Task-ready declarations generated by S5 SHALL NOT make their provider contracts ready. (Design 8.0.2: §5.2.1, §5.6.5.2-§5.6.5.4, §10.2.1; pipeline design 2.0.2 §5.2.1-§5.2.2, §5.4; M1-5.)

#### Scenario: Existing Plan data determines one rendering view
- **WHEN** all exports use supported C99 forms and every declaration, implementation source, dependency, and entry slot has one declared binding
- **THEN** repeated derivation emits byte-identical ordered rendering views bound to the same Plan and Blueprint

#### Scenario: A function implementation slot is ambiguous
- **WHEN** a task-ready function can map to more than one eligible provider source or to none
- **THEN** preflight identifies the affected contract/export and fails before workspace mutation without changing the Plan or invoking an LLM

#### Scenario: A declaration requires an undeclared symbol
- **WHEN** a type or constant declaration references a non-built-in symbol with no unique exported interface binding
- **THEN** preflight rejects the rendering view instead of inventing a declaration or include

### Requirement: E0 rendering is deterministic and protocol neutral
For every expanded Blueprint file rule, S5 SHALL use its declared producer, mutability, render rule, contract, build role, owner, and template path to render exactly one active workspace file. S5-frozen headers, mechanical sources, build files, and documents SHALL be complete deterministic outputs. S6-owned implementation files SHALL contain only compilable stubs for their assigned declarations; every unused parameter SHALL be consumed and every ordinary function SHALL return the mechanically derived NOT_IMPLEMENTED result. The unique entry source for each executable SHALL use the protocol-neutral POSIX wait/SIGTERM behavior and SHALL not implement protocol behavior. Rendering SHALL use only frozen structured inputs and declared language rules, SHALL produce no undeclared active source path, and SHALL contain no protocol-specific constant or branch originating from template/framework source. (Design 8.0.2: §5.2.1, §5.6.5.1-§5.6.5.4, §6.5, §7.4; pipeline design 2.0.2 §5.4-§5.5; D1.7/D1.11; M1-5.)

#### Scenario: Two protocol fixtures use one renderer
- **WHEN** version-controlled S4-produced MQTT and non-MQTT fixture Plans with different layouts are materialized
- **THEN** both workspaces follow their own Blueprint paths and symbols through the same renderer and the non-MQTT output contains no MQTT residue

#### Scenario: An unimplemented function is called
- **WHEN** a generated ordinary function stub is invoked with valid arguments
- **THEN** it returns the derived NOT_IMPLEMENTED value without aborting, asserting, or claiming task completion

#### Scenario: The generated executable is started
- **WHEN** the Blueprint-declared executable is launched without arguments
- **THEN** its generated entry remains alive awaiting termination and contains no protocol implementation

### Requirement: E0 build and smoke are hard acceptance gates
S5 SHALL execute every default build variant in the configured sandbox with network disabled and SHALL bind each result to the candidate workspace tree, variant, command, exit status, stdout/stderr, duration, and timeout state. C99 release and sanitizer builds SHALL use the design-defined compiler flags and SHALL complete with zero warnings and errors. For each executable artifact and each default variant, S5 SHALL launch the Blueprint-declared output with no arguments from the workspace root, require it to remain alive for configured `smoke.dwell_seconds`, send SIGTERM, require exit within `smoke.term_grace_seconds`, normalize an observed SIGTERM exit to 143, and reject sanitizer reports. Test Bundle tests SHALL NOT run in M1-5. (Design 8.0.2: §6.5, §7.4, §8.3, §8.5; pipeline design 2.0.2 §5.4-§5.5; D1.1; M1-5.)

#### Scenario: All E0 variants pass
- **WHEN** every default variant builds warning-free and each declared executable passes dwell, SIGTERM, grace, exit-code, and sanitizer checks
- **THEN** S5 may create the E0 checkpoint and the persisted build/smoke result refs identify all accepted checks

#### Scenario: A process exits before dwell completes
- **WHEN** a generated executable exits on its own before the configured dwell interval
- **THEN** smoke fails and S5 does not publish a ready epoch or binding

#### Scenario: Generated code is about to run on the host
- **WHEN** a build or smoke request cannot be executed through the configured isolated sandbox
- **THEN** S5 reports an internal tool failure and does not execute generated code directly on the host

### Requirement: E0 publishes closed manifests, ledgers, receipts, and stage anchors
After successful build and smoke, S5 SHALL create exactly one initial git repository and checkpoint commit whose trailers bind E0 and Plan 1.0.0. It SHALL publish canonical schema-valid artifact manifest and contract map projections for every expanded file, build artifact, contract/export, implementation file, stage creator, mutability, owner task, and Plan/Blueprint/epoch binding. The E0 file ledger SHALL preserve every `s6_owned` stub as `slot_only` and SHALL mark each accepted `s5_frozen` file `realized` with its checkpoint content/commit/build evidence and S5 epoch provenance but no task owner. The immutable epoch receipt SHALL bind E0, Plan, Blueprint, checkpoint tree/commit, `materialization_status=ready`, all build/smoke result refs, and no pending group. The immutable 1.0.0 binding receipt SHALL bind that epoch receipt and immutable manifest/map copies; root manifest/map files SHALL be current deterministic copies rather than historical authority. Run S5 output refs SHALL identify the accepted epoch and binding receipts. (Design 8.0.2: §5.6.5.4, §5.6.7, §6.5; pipeline design 2.0.2 §3.3, §4.2, §5.4; D1.7; M1-5.)

#### Scenario: Ready E0 is sealed
- **WHEN** rendering, all builds, and all smoke checks pass and the checkpoint commit is valid
- **THEN** manifest, contract map, file ledger, epoch receipt, binding receipt, current copies, and S5 Run refs form one recomputable binding for Plan 1.0.0/E0

#### Scenario: A task-owned stub is recorded
- **WHEN** S5 creates an `s6_owned` source for its future owner task
- **THEN** the manifest records that owner while the file-ledger row remains `slot_only` with no fabricated implementation or verification evidence

#### Scenario: A frozen generated file is recorded
- **WHEN** S5 creates an `s5_frozen` file accepted by E0 build and smoke
- **THEN** its file-ledger row is `realized`, points to S5/checkpoint evidence, and carries no task-owner history

### Requirement: S5 publication and recovery converge on one accepted checkpoint
S5 SHALL stage its expected E0 tree and public artifact values under the run lock before publication. It SHALL treat the valid epoch checkpoint commit as the workspace commit point and the atomic `run.stages.s5=done` update with typed epoch/binding output refs as the S5 acceptance point. Receipt construction SHALL avoid hash cycles: the epoch receipt SHALL not reference a future binding or a file-ledger value that references the receipt, and the binding SHALL be created only after the epoch receipt. Recovery SHALL run before S5 admission, use the current E0 staging/WAL and exact tree/hashes, remove or replace only uncommitted outputs from this attempt, reuse a valid existing checkpoint to reproduce the same canonical receipts, and move only forward after the checkpoint exists. After the S5 Run acceptance point, recovery SHALL append a missing byte-identical `epoch_materialized` event without rerendering. Conflicting checkpoint, receipt, binding, ledger, current-copy, Run ref, or event bytes SHALL fail as artifact damage and SHALL never be guessed, overwritten, or repaired by an LLM. (Design 8.0.2: §4.8, §5.6.7, §6.5; pipeline design 2.0.2 §4.4, §5.4; D1.4/D1.15; M1-5.)

#### Scenario: Crash occurs before the checkpoint
- **WHEN** S5 is interrupted after staging or workspace rendering but before a valid E0 checkpoint commit
- **THEN** resume removes only this attempt's uncommitted outputs, revalidates admission, and deterministically rematerializes E0

#### Scenario: Crash occurs after the checkpoint
- **WHEN** the valid E0 checkpoint exists but one or more receipts, current copies, ledger values, or the S5 Run update are absent
- **THEN** resume verifies the exact checkpoint and completes the missing canonical suffix without a second git initialization or a second checkpoint

#### Scenario: Materialization event is missing
- **WHEN** the S5 Run receipt is accepted but the matching `epoch_materialized` event is absent
- **THEN** recovery validates the accepted refs and appends exactly one matching event without changing the workspace or receipts

### Requirement: Completed E0 replay is a zero-change operation
If the current S5 instance is already done for E0 and its Plan, Blueprint, checkpoint, receipts, binding, ledgers, current copies, Run refs, and materialization event all validate, another S5 invocation SHALL return the existing accepted result without changing workspace files, git refs, artifact bytes, event count, or timestamps. A conflicting completed instance SHALL fail closed as artifact damage. (Design 8.0.2: §4.8, §6.5; pipeline design 2.0.2 §4.4, §5.4; D1.12; M1-5.)

#### Scenario: E0 is invoked twice
- **WHEN** a valid completed E0 invocation is repeated with the same sealed inputs
- **THEN** the second invocation produces zero file and git changes and returns the existing output refs

#### Scenario: A sealed receipt was altered
- **WHEN** replay finds that an accepted receipt or binding no longer matches its Run ref or checkpoint
- **THEN** S5 reports artifact damage and does not regenerate the accepted artifact in place

### Requirement: S5 failure semantics remain bounded and observable
Input, seal, Blueprint, lint, or renderability rejection SHALL mark the current S5 instance failed through the existing controlled stage-failure/report path and SHALL not increment `internal_error_count`. A deterministic template, sandbox tool, git operation, E0 build, or E0 smoke failure that prevents S5 from satisfying its own fixed contract SHALL terminate as `internal_error`. Every failure SHALL retain the structured stage diagnostic and any valid pre-failure evidence, SHALL perform no LLM call or Fixer retry, and SHALL not publish `materialization_status=ready`, initialize Plan State, run S6, or generate Test Bundle assets. (Design 8.0.2: §4.7-§4.8, §6.5, §10.2.1-§10.2.2; pipeline design 2.0.2 §5.4-§5.5; D1.10; M1-5.)

#### Scenario: A sealed Plan is not renderable
- **WHEN** preflight proves a concrete missing declaration, definition binding, or entry binding in the existing S4 output
- **THEN** S5 records that exact blocker as a controlled failure with no workspace publication and does not reopen architecture calibration

#### Scenario: The fixed template cannot build
- **WHEN** valid admitted inputs render through the supported template but E0 compilation or smoke fails because the deterministic S5 output cannot meet its contract
- **THEN** the run terminates as `internal_error`, no ready receipt is published, and no LLM repair is attempted
