# NePA 后续阶段需求与优先级

状态：P0–P2 已由用户自动执行目标授权；P3–P5 保持后续需求草案

记录日期：2026-09-13

适用基线：`codex/protocol-behavior-and-http`，调查时 HEAD `10cb987178c329cefb909c8651a2daa9e9c548b5`

## 1. 文档目的

本文记录 NePA 在当前端到端重构之后的后续目标、优先级、依赖关系和可验收条件。它不是对
`project_docs/system_design.md` 的直接修改，也不代表已经批准实现或启动付费实验。进入每个阶段前，
应先把经确认的需求写入权威设计，再实施和验收。

长期目标保持不变：给定协议事实和目标格式，NePA 能够使用不同能力、不同供应商的模型，稳定生成
可构建、可运行、通过独立协议验收的项目；进一步把上游 RFC 转换为可审查、可追踪的 Spec。

## 2. 已核实的当前基线

以下结论来自当前工作区的代码和设计，不把正在进行的实验视为已经完成的能力：

1. DeepSeek 已完成过一次 MQTT 最小端到端成功案例，证明现有核心链路可行；它不能证明三次稳定性、
   其他协议、其他模型或完整 MQTT 合规。
2. 当前分支正在扩展 MQTT 行为检查和 HTTP 固定长度子集验证。这些属于在途工作，只有最终报告、
   构建和独立交互证据一致后才能记为通过。
3. `nepa/speclib/plan.py` 仍把每个任务的 `depends_on` 指向前一个任务；
   `nepa/orchestrator.py` 每次只执行第一个未完成任务。因此目前是单链规划、单任务串行执行。
4. 单写者和每任务 checkpoint 能减少共享工程损坏，但当前把本来独立的消息编解码任务也强制串行，
   造成明显的墙钟时间浪费。
5. 当前代码智能体能够读取运行目录下的 `inputs/checks`，编码容器也挂载 `/checks`。虽然它不能修改
   验收资产，但它可以针对脚本内容定向实现，因而现有成功证据不足以排除对验收用例的过拟合。
6. 已有 Qwen 的 OpenAI-compatible provider 入口，但没有本文指定的两个 Qwen 3.7 模型配置、人民币
   价格、能力探测记录或正式端到端证据。
7. 当前核心仍以人工整理的 Spec 3.0 为输入，不包含 RFC 抓取、规范性语句抽取、事实归一化和人工
   审批后的 Spec 发布流程。
8. 当前预算机制已经支持人民币单次上限、活动累计上限、预留和实际 usage 结算。这部分应被并发和
   多供应商实验复用，而不是另建一套旁路计费。

## 3. 总体优先级

| 优先级 | 目标 | 排序理由 | 主要依赖 |
|---|---|---|---|
| P0 | 固化当前协议扩展基线 | 为后续优化提供可比较的串行、DeepSeek、可复现基准；不是新增功能 | 当前在途 MQTT/HTTP 工作收口 |
| P1 | 隔离私有验收资产 | 决定后续所有成功证据是否可信；必须先消除“看答案实现” | P0 的验收资产和结果格式 |
| P2 | 建立模型能力适配并验证 Qwen 3.7 | 先验证 NePA 是否真正模型无关，并暴露 provider/action/prompt 假设 | P1，稳定的串行基线 |
| P3 | 依赖图、优先级和分批并行执行 | 减少端到端墙钟时间，同时避免共享工程并发写入 | P1；最好以 P2 的双模型证据校验通用性 |
| P4 | 支持较弱、廉价模型 | 在可信验收、跨供应商和安全调度基础上做成本优化 | P1–P3 |
| P5 | 打通 RFC → Spec | 扩展产品输入边界，且必须避免“自动抽取、自动证明”的闭环偏差 | 稳定的 Spec 合同和下游验收 |

P1 和 P2 的实施应先于并行生产启用。P3 的设计和原型可以提前进行，但在私有验收没有隔离、Qwen
失败原因还无法清楚归类时，不应把并发设为默认路径；否则只会更快地产生难以解释的失败和不可信的
成功。P4、P5 不应阻塞 P1–P3。

## 4. P0：固化可比较的当前基线

### 4.1 需求

- 保留 DeepSeek 首次成功案例的输入摘要、代码版本、模型配置、成本、任务记录、构建、交互和导出证据。
- 待当前 MQTT 扩展和 HTTP 子集工作结束后，分别明确记录“通过、失败或未完成”，不能把测试收集、
  局部测试或正在运行等同于成功。
- 记录串行基线的总墙钟时间、各任务模型等待时间、工具/构建时间、token、人民币费用、重试次数、
  失败类型和模型分工。P3 的提速必须与同一口径比较。
- 固定一组公共的 provider-neutral 小型会话测试，以及 MQTT/HTTP 私有端到端验收。后续不得为了让
  某个模型或并发版本通过而降低这些标准。

### 4.2 完成条件

- 基线报告可以回答时间和费用主要消耗在哪些任务、哪些模型调用和哪些重试。
- 所有参与后续对比的输入、镜像、提示词和验收资产都有摘要；差异会使样本被标记为不同候选版本。
- 没有覆盖或迁移历史运行工件。

## 5. P1：代码生成与私有验收彻底分离

### 5.1 目标

代码智能体只能看到协议 Spec、Target、当前生成工程和明确公开的开发检查；它不能读取、搜索、执行、
通过间接日志还原或从路径推测最终私有验收脚本。最终是否成功只能由宿主控制的独立验证环境判断。

### 5.2 功能需求

#### ACC-001：物理存储隔离

- 私有 Acceptance manifest、脚本、测试向量和随机种子不得位于 agent-visible 的 `inputs` 或生成工程中。
- 编码沙箱不得挂载 `/checks`、私有验收目录或包含其副本的 evidence 目录。
- 验收沙箱只读挂载私有资产，并只把生成工程或产物作为被测对象。

#### ACC-002：所有访问路径一致封闭

- `list_files`、`read_file`、`search`、`run_command` 和符号链接都不能绕过隔离。
- 代码智能体不能通过宿主绝对路径、容器挂载路径、历史调用记录或错误栈获得脚本内容。
- 私有验收不得被打包进最终交付工程。

#### ACC-003：有限、结构化的失败反馈

- 验收失败时，可向修复会话返回检查 ID、场景类别、观察到的协议结果、相关服务端 stdout/stderr、
  构建或 sanitizer 状态。
- 不返回脚本源码、完整实现逻辑、私有随机种子或足以逐字复现测试实现的内部路径。
- 反馈必须足以支持根因修复；“完全不给诊断”不是隔离目标。

#### ACC-004：防止只记住固定向量

- 在协议允许范围内动态选择端口、client ID、合法载荷、拆包/粘包方式和重复次数。
- 随机种子和实际字节交互保存在宿主证据中，保证问题可复现，但不在生成阶段暴露。
- 公开开发测试与私有最终验收必须在报告中分栏，不能混称为独立验收。

#### ACC-005：证据与历史结果说明

- RunStore 保存私有资产摘要、验证器版本、执行结果和证据引用，不保存到 agent-visible 上下文。
- 隔离之前的成功案例仍可作为链路可行性证据，但不能作为排除“针对验收脚本实现”的最强证据。
- 迁移现有验收时不得减少 MQTT/HTTP 检查内容。

### 5.3 验收条件

- 自动测试证明智能体从所有文件/命令动作均无法读取私有资产，包括符号链接和绝对路径尝试。
- 同一私有脚本在验证沙箱中能够正常启动服务、执行交互并收集完整证据。
- 正确项目通过，错误响应、只休眠服务、硬编码单一 client ID、固定端口、提前退出和 sanitizer 问题失败。
- 修复会话只能使用脱敏诊断完成修复；最终报告明确哪些检查是私有独立检查。

## 6. P2：Qwen 3.7 与模型无关能力

### 6.1 首批目标模型

- 推理/困难任务：`qwen3.7-plus-2026-05-26`
- 快速/常规任务：`qwen3.7-flash-2026-07-15`

这两个名称是用户指定的目标 ID。首次付费调用前必须通过阿里云百炼/DashScope 当前账户的模型列表或
官方文档确认：ID 可用、地域和 endpoint、上下文/输出上限、思考控制方式、结构化输出或工具调用能力、
usage/cache 字段及人民币价格。未经核实不得猜测价格或把相近名称静默替换为指定模型。

### 6.2 模型无关合同

#### MODEL-001：统一能力描述，不要求请求报文完全相同

provider profile 应显式描述：

- streaming、JSON object 和原生 tool call 支持；
- 思考模式及其对 token/输出结构的影响；
- 最大上下文、最大输出、stop/temperature 限制；
- usage、cache hit/miss、返回模型身份和错误分类；
- 可重试网络错误与不可重试请求错误。

规划器、工作区工具、任务通过条件和验收标准保持 provider-neutral。各 provider adapter 可以根据能力
产生不同的合法 wire request，但不得改变任务语义或成功标准。

#### MODEL-002：配置与计费

- Qwen 模型和价格放在可审计的配置 profile 中，不硬编码进规划器或协议提示词。
- 每次记录请求的目标模型、供应商返回的实际模型、输入/输出/缓存/思考 token 和人民币估算。
- 模型身份不匹配、usage 缺失或未知调用沿用现有保守预留机制，不能按零成本处理。
- Qwen 证明运行不得在失败时静默回退到 DeepSeek；否则只能报告混合模型运行，不能报告 Qwen 成功。

#### MODEL-003：Qwen 任务路由

初始路由沿用当前经验证思路，但由任务属性而非协议名称决定：

- Qwen Flash：bootstrap、普通 message、首次普通 requirements 批次。
- Qwen Plus：共享 wire/公共接口、高影响整合、final-integration、编译或私有验收失败后的困难修复。
- 路由必须记录实际原因；若实验表明某类任务需要调整，应修改通用难度规则而不是加入 MQTT/Qwen 特例。

#### MODEL-004：分级实验

1. 能力探测：验证精确模型 ID、结构化动作、usage 和错误处理，限制为小额、短会话。
2. 工具会话测试：读文件、改文件、编译失败、读诊断、修复、finish，确认两种模型均遵守动作合同。
3. 一次全新 MQTT 可行性运行：只使用 Qwen 组合和私有验收，从空工程开始。
4. 根因分类与通用优化：区分 provider adapter、动作协议、上下文管理、任务设计、生成代码语义和验证器问题。
5. 候选版本冻结后，再进行两次全新重复；三次均通过才能宣称“Qwen 组合在当前 MQTT 验收范围内稳定”。
6. 当前 HTTP 子集基线稳定后，用同一候选做一次跨协议验证，避免把 MQTT 单协议成功误称为模型无关。

### 6.3 预算默认解释

“费用上限与 DeepSeek 目前设置的一样”在本文暂按以下方式解释：

- 新建独立 Qwen 人民币活动根目录，不与 DeepSeek 历史账本混用；
- 每次生成最多 CNY20、四小时；
- Qwen 活动累计最多 CNY300，能力探测、失败、恢复和未知预留均计入；
- 不启用响应缓存，不复用已有生成工程；
- 未核实官方价格并写入配置前，不开始完整付费运行。

用户随后授权全部合理决策自主执行；本轮采用以上独立 CNY300、单次 CNY20／4 小时解释。

### 6.4 完成条件

- Qwen 两个模型均通过动作合同测试，实际模型身份和费用可审计。
- 从空工程完成一次 MQTT 成功后，冻结候选并完成两次全新成功重复；期间不人工修改生成项目。
- 至少对当前 HTTP 子集完成一次同标准验证，或明确标记“只验证 MQTT，尚未证明跨协议”。
- 所有失败都有分类证据，修复不引入协议名、消息常量、需求编号或 Qwen 专属语义分支。

## 7. P3：任务依赖图、优先级与分批并行

### 7.1 目标与边界

目标是减少墙钟时间，而不是同时让多个会话直接修改同一个工程。不能恢复旧式冻结 ABI、文件租约或
最后写入者覆盖机制。并行结果必须可确定地集成、构建、回滚和恢复。

### 7.2 规划需求

#### PAR-001：Plan 从单链升级为依赖图

- 每个任务的 `depends_on` 改为依赖集合；相同输入仍产生确定性 Plan。
- bootstrap 是根任务；shared-wire 依赖 bootstrap。
- 消息任务依赖 shared-wire，以及其结构引用真正需要的前置任务；互不引用的消息任务可并行。
- requirement 任务继续保持每条需求唯一主任务，但“每 12 条”只作为规模上限。任务应按 Spec 中显式
  引用的消息、类型、角色、状态或共享资源聚类，不从协议名和需求编号前缀猜测。
- final-integration 依赖所有实现任务和必要修订任务。
- 对依赖不确定或共同修改高风险共享接口的任务，默认保守串行，而不是乐观并发覆盖。

#### PAR-002：就绪队列和优先级

只调度所有依赖已经接受的 ready task。优先级至少考虑：

1. 关键路径长度和能够解锁的下游任务数；
2. 共享接口影响范围；
3. 是否是失败后的修复或阻塞任务；
4. 估算的上下文、token 和执行时长；
5. 可用模型能力与活动剩余预算。

不得根据 MQTT 名称、固定消息常量或需求 ID 模式给予特殊优先级。相同状态下使用稳定 task ID 排序，
保证调度可复现。

#### PAR-003：分批执行

第一版建议采用以下 wave，并从最大并发 2 开始：

1. bootstrap 单独执行并接受 checkpoint；
2. shared-wire 单独执行并接受 checkpoint；
3. 从相同 checkpoint 派生若干独立 message 工作副本，按 ready queue 分批执行；
4. 对已满足真实依赖的 requirement 任务分批执行；
5. final-integration 单独执行；
6. 私有验收修复按实际影响重新生成依赖，不能绕过失败任务预算。

只有数据证明冲突率、失败率、费用和宿主资源可控后，才把并发从 2 提升；并发数必须受 CPU、内存、
provider 限流和活动预算共同约束。

### 7.3 隔离与集成需求

#### PAR-004：并行任务不能直接写权威工程

- 每个任务从同一个已接受 checkpoint 建立独立 Git worktree 或等价隔离工作副本。
- 任务输出是补丁、需求声明、构建结果和证据；任务本身不能推进权威 Run 状态。
- 单一集成写者按确定顺序应用补丁，每应用一个补丁即构建并保存集成结果。

#### PAR-005：冲突处理

- 文本冲突、共享接口变更、补丁基线不匹配或集成构建失败不能使用 last-writer-wins。
- 失败任务应基于最新已接受集成 checkpoint 重新执行或进入显式修复任务。
- 已完成并行尝试及其费用保留为证据，恢复不能重复接受任务或清零预算。
- 一个任务对共享头文件的修改必须同步修复调用方；不能用预先冻结的 C ABI 阻止合理重构。

#### PAR-006：并发预算安全

- 调用前预算预留必须使用现有活动级原子锁；所有并行进程看到同一真实剩余额度。
- 预留失败的任务不得发起请求；未知调用保留峰值预留。
- 任务取消不能杀死无关运行，也不能删除其他工作副本或证据。

### 7.4 性能和正确性验收

- 对同一冻结候选分别运行串行和并行版本，比较完整墙钟分解、token、费用、冲突、重跑和通过率。
- 并行版不得跳过任务、需求声明、逐任务构建、最终清洁构建或私有验收。
- 第一阶段目标：成功运行墙钟时间中位数至少降低 25%，人民币费用中位数不比串行基线增加 10% 以上；
  若达不到，保留数据并回到串行默认，不为了宣称提速降低验收。
- 并发中断、单任务失败、集成冲突、预算不足和宿主重启均能从最后已接受 checkpoint 恢复。
- 使用 DeepSeek 和 Qwen 各至少验证一次，防止调度器依赖某个模型独有的输出习惯。

## 8. P4：让较弱、廉价模型完成任务

### 8.1 两种必须分开报告的模式

1. **纯弱模型模式**：整个生成和修复过程不调用更强模型。只有这种模式能证明弱模型独立完成。
2. **经济混合模式**：廉价模型完成大部分任务，强模型只处理高影响任务或有界升级。报告强弱模型的
   任务比例、token、费用和触发原因，不能称为“弱模型独立成功”。

初始候选包括 Qwen 3.5 Plus/Flash 和更旧模型；具体可用 ID、价格和能力应在开始实验时核实，不能仅凭
产品族名称配置。

### 8.2 框架改进原则

- 将任务缩小为语义内聚单元，同时保留完整依赖事实，不能只按固定条数机械切分。
- 给出明确的完成条件、现有接口、相关事实切片和最新诊断，减少让弱模型自行猜测全局状态。
- 用确定性的通用工具完成 schema 校验、构建、诊断归一化和补丁应用；不把协议答案写进 helper。
- 对重复无效动作、连续相同编译失败、共享接口高影响修改、sanitizer 或私有验收失败设置可审计的升级信号。
- provider 支持且实验结果更好时使用原生工具调用；始终保留经过测试的通用 JSON 动作后备格式。
- 压缩上下文时保留完整事实引用、最近有效文件观察和真实错误，不用摘要替换关键协议约束。

### 8.3 基准与完成条件

- 先用小型动作、局部编译修复、跨文件接口修改、需求实现和 final-integration 构成能力阶梯，再运行
  完整私有端到端验收。
- 每个候选记录动作合法率、首次构建成功率、重试/升级数、墙钟、成本和最终通过率。
- 一个 fixture 或一次成功不能证明支持；选定候选应先成功一次，再冻结配置完成两次全新重复。
- 同时报告纯弱模型和经济混合模式；混合模式应相对当前强模型基线显著降低人民币成本，且验收标准不变。
- 所有改进保持协议和模型中立，不为某个 benchmark 加入隐藏答案或固定代码模板。

## 9. P5：RFC → Spec

### 9.1 第一阶段范围

先支持可稳定解析的 RFC HTML/TXT 和明确版本，不在第一阶段同时承诺任意 PDF、图片 OCR、互联网规范
发现、自动测试生成或完全无人审查。自动产生的 Spec 必须经过独立 lint 和人工批准后，才能成为代码
生成输入。

### 9.2 流程需求

1. **来源冻结**：保存 RFC URI、版本/日期、原始字节摘要和章节锚点；同名不同版本不能静默替换。
2. **规范性语句抽取**：识别 MUST/SHOULD/MAY 及其否定形式、适用角色、条件和例外，保留原文引用。
3. **协议事实归一化**：抽取 transport、types、messages、字段、位域、长度、状态、方向、错误响应和时序。
4. **关系建立**：把需求与消息、类型、状态和章节建立显式引用，不从编号或标题推断缺失关系。
5. **冲突与缺口报告**：标记重复、互相矛盾、来源缺失、无法结构化和需要人工判断的事实，不凭模型猜测补齐。
6. **Spec 3.0 lint**：验证 ID、引用、类型闭包、角色方向、来源和结构完整性；结构通过不宣称语义正确。
7. **人工审批发布**：审阅差异、引用和未决项后发布不可变 Spec 快照；只有已批准快照进入 NePA。
8. **回归比较**：以现有手写 MQTT 和 HTTP Spec 为金标准，比较需求召回、事实差异、错误引用和下游生成结果。

### 9.3 独立性要求

- RFC→Spec 模型不能看到目标项目源码或私有协议验收脚本。
- 第一阶段不让同一流程根据自己生成的 Spec 自动生成最终验收，以免形成自证闭环。
- 私有验收仍由独立来源维护；Spec 抽取质量和生成项目质量分别报告。
- 每条生成事实必须有精确 RFC 章节引用；没有来源的推断只能作为待人工确认项，不能混入已接受事实。

### 9.4 完成条件

- 对选定 RFC，规范性要求和结构事实的人工抽样精度、召回率达到事先约定阈值。
- 零伪造章节引用；所有无法确认的内容均显式列入 gap report。
- 自动 Spec 与手写 Spec 的语义差异可审查、可定位到来源。
- 人工批准后的自动 Spec 能进入同一 provider-neutral 生成链路，并通过相同的独立验收；结果不能反向降低抽取标准。

## 10. 跨阶段共同约束

1. NePA 核心不得识别 MQTT/HTTP 名称、固定消息常量、需求编号或某个 fixture；协议知识只能来自输入。
2. 不得为提高通过率而泄露或削弱私有验收、导入已有目标源码、使用响应缓存或人工修补生成项目。
3. 每项优化必须同时记录质量、墙钟、token、人民币费用和失败分类；只降低某一个指标不等于完成。
4. 新模型、新调度器和 RFC 抽取均先做小规模能力探测，再做一次可行性运行，最后冻结候选并做重复验证。
5. 运行、预算、调用、checkpoint 和证据必须可恢复且不可静默覆盖；并行进程共享同一个原子活动预算。
6. 实施发现权威设计需要变更时，先说明证据和影响并取得用户对设计文档修改的明确授权。
7. 当前文档不授权推送、合并、部署或清理历史运行。

## 11. 建议执行顺序

```text
当前 MQTT/HTTP 在途工作收口并冻结串行基线
  → 私有验收物理隔离和回归验证
  → Qwen 3.7 能力探测与一次 MQTT 可行性运行
  → 通用问题修复，冻结 Qwen 候选并完成两次重复
  → 依赖图/隔离工作副本/单写者集成，先并发 2
  → DeepSeek 与 Qwen 串并行对照，达到提速门槛后设为默认
  → Qwen 3.5 和更旧模型的纯弱模型/经济混合模式
  → RFC HTML/TXT → 可追踪 Spec → 人工审批 → 同一生成链路
```

P3 的代码设计可与 Qwen 实验准备并行开展，但不得在 P1 完成前用新的并发路径生成正式成功证据。

## 12. 待用户确认的决策

本文使用了以下默认解释。若用户没有异议，可在后续设计阶段按推荐项执行：

1. **Qwen 预算**：推荐单独建立 CNY300 的 Qwen 活动预算，每次最多 CNY20、四小时，而不是与 DeepSeek
   共用同一活动账本。
2. **Qwen 支持范围**：推荐先以 MQTT 私有验收完成“一次成功＋冻结后两次重复”，再用 HTTP 子集补充
   跨协议证据；不要等待两个协议都完成才开始第一次诊断。
3. **并发强度**：推荐初始最大并发 2，以至少 25% 墙钟下降且费用增加不超过 10% 为推广门槛。
4. **弱模型成功口径**：推荐同时建设纯弱模型和经济混合模式，但在报告中严格分开。
5. **RFC 输入和审批**：推荐第一阶段只做 HTML/TXT，必须人工批准 Spec；PDF/OCR 和自动测试生成后置。
