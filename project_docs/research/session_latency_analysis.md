## 机制判断与下一候选优先级

适配器只在普通文本中提供 Schema／提示，没有发送 `response_format`。提示已禁止 XML／DSML／invoke
标签并给出合法 JSON 样例，但真实响应仍反复产生包装文本。继续增加提示警告未能消除问题；不能通过
宽松解析 XML 或抓取畸形输出中的嵌套对象，把这些调用算成成功动作。

2026-09-12 核对的 DeepSeek JSON Output 官方文档表明支持
`response_format={"type":"json_object"}`，仍要求提示包含 JSON 示例和足够输出额度，也可能返回空内容。
因此在既有请求／适配器链路增加显式 JSON 输出，同时保留严格宿主 Schema。wire 计量、请求证据和预算
预留必须包含该字段，并测试真实序列化及畸形／空响应拒绝。

同日核对的 thinking-mode 文档说明思考默认 high effort 且忽略 temperature；temperature 0 不能证明生成
确定性。不能为宣称提速而盲目关闭或降低复杂编码任务的推理。应先消除有证据的输出合同浪费，保持推理、
输出／上下文容量、110 条需求、任务／会话额度、checkpoint、构建和独立 oracle 不变。原生工具涉及另一套
对话／reasoning 合同，只有较小的 JSON 模式修复失败后才值得引入。

当前实验继续使用既有生产运行时；任何候选变化都需要新的空工程验证，混合版本第一次运行不能作为新候选
稳定性证据。
