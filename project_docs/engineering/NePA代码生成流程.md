# NePA 代码生成流程

本文描述当前 NePA 的实际代码生成链路：由确定性计划控制流程，由 LLM 代码智能体在受限工作区内实现任务，并通过真实构建、测试反馈和最终独立验收闭合结果。

## 1. 总体流程

```text
Spec / Target / Acceptance
          ↓
输入校验、快照和确定性计划
          ↓
串行领取任务
          ↓
模型读代码 → 修改 → 编译/测试 → 获取反馈 → 继续修复
          ↓
任务 finish + 构建通过
          ↓
最终集成、独立验收和导出
```

NePA 当前不是让模型自由规划整条流程，也不是多个 Agent 并行生成代码，而是由固定的 Orchestrator 按计划串行推进任务。

## 2. 输入冻结与计划生成

`nepa run` 首先读取 Spec、Target、Acceptance 和配置，并执行输入 lint。随后 RunStore 会：

- 将 Spec、Target、Acceptance 及验收脚本复制到本次 run 的 `inputs/` 和 `inputs/checks/`；
- 保存 SHA256，防止运行期间输入漂移；
- 根据 Spec 和 Target 编译确定性 Plan；
- 创建空的 `project/`、证据目录和 Git checkpoint；
- 初始化任务状态、预算、调用记录和恢复信息。

计划由 `compile_plan` 生成，任务之间形成单一串行依赖链。以 MQTT 为例，当前计划共有 23 个任务：

- `bootstrap`：创建工程、Makefile、README 和启动/退出路径；
- `shared-wire`：实现公共字节流、报文帧和编码基础；
- 10 个 `message:*` 任务：分别实现 MQTT 报文；
- `requirements:001`～`requirements:010`：分批实现全部 110 条需求；
- `final-integration`：最终集成和独立验收。

## 3. 普通任务的代码生成循环

Orchestrator 每次选择第一个尚未通过的任务，创建一个 CodingSession。普通任务的基本过程是：

1. 将当前任务、相关需求、Target、Spec 索引、任务流水线和已有反馈放入模型上下文；
2. 模型通过工具读取当前工程和只读的输入/测试资产；
3. 模型返回一个动作；
4. NePA 严格校验动作格式；
5. 执行动作并保存结果；
6. 模型根据结果继续修改、测试或提交 `finish`；
7. `finish` 时验证需求声明、代码引用并执行 release/san 构建；
8. 构建通过后提交任务 checkpoint，任务状态变为 `passed`。

一个普通任务完成时，系统自动做的是构建检查，不是完整 acceptance。模型可以在任务内部主动运行局部测试或验收场景，但这不是固定强制步骤。

## 4. 模型动作与工作区边界

模型每轮只能产生一个有效动作。当前主要动作包括：

- `list_files`、`read_file`、`search`：发现和理解代码；
- `write_file`、`replace_text`：修改生成工程；
- `run_command`：在隔离 sandbox 中编译、运行程序或执行测试；
- `finish`：提交任务完成声明；
- `request_followup`：为非最终集成任务请求一个有证据引用的后续任务。

生成工程可写，`inputs/`、验收脚本和 `evidence/` 只读。命令通过 sandbox 执行，并受到网络、CPU、内存和超时限制。模型不能修改 Spec、Target 或验收脚本来绕过检查。

当前配置默认使用严格的 `json_object` 动作格式；格式错误、缺字段或不完整响应不会执行任何工具，但会留下反馈并消耗本次调用的预算。

## 5. 上下文、反馈与任务内修复

CodingSession 会将每次工具结果保存为证据。上下文包含两类关键状态：

- `current_observations`：模型成功读取的当前文件内容及其 SHA256；
- `latest_observed_diagnostic`：最近一次构建失败、测试失败、超时、工具错误或非零退出结果。

模型可以先读 acceptance 源码，再结合当前 C 源码和实际测试输出定位问题。例如 `pubsub` 超时时，模型能够看到订阅、发布、消息转发和超时判断的实际测试逻辑，而不只是一个失败标记。

如果已读取的文件后来被修改，旧 observation 会因 SHA256 不一致而失效。较早的交互历史在上下文超限时可以淘汰，但当前任务事实、当前文件观察和最近诊断不会被静默丢弃。

普通任务的修复通常由模型主动触发：修改后运行构建或局部测试，收到失败反馈后继续修改。任务的 session 和 decision 数量受配置限制；耗尽后任务失败，run 不会跳过该任务。

## 6. 最终集成、验收与导出

所有普通任务通过后，Orchestrator 才进入最终集成：

1. 将当前工程复制到新的 `export-attempts/` 目录；
2. 要求存在 README 和 C 源文件；
3. 执行干净的 release 和 sanitizer 构建；
4. 分别启动两个构建产物；
5. 顺序执行 Acceptance 中的全部必需场景；
6. 记录每个场景的命令、返回码、stdout、stderr、超时和 `passed` 状态；
7. 检查服务端退出码、停止超时和 Sanitizer 错误；
8. 全部通过后，将 export 原子移动为 `delivery/`，保存文件树哈希和 checkpoint。

如果最终导出检查失败，系统将失败结果传给 `final-integration` 修复，并在有限次数内重新构建和验收。最终验收通过前，不会发布 delivery。

## 7. 恢复、证据和计费

每次模型调用、工具动作、构建、测试和最终导出都会写入 run 的证据目录。RunStore 同时维护：

- 当前任务和任务状态；
- 已接受 checkpoint；
- 项目工作树哈希；
- 输入、配置和运行时代码哈希；
- LLM 调用、token、成本和未结算预留；
- 最终报告和导出结果。

`resume` 会先校验输入、配置、运行时代码和 checkpoint。若上次运行中断，会保留中断工作树并恢复到最近接受的 checkpoint，再继续执行。当前默认成本核算为 CNY，预算、调用次数和墙钟时间均在外部调用前检查。

## 8. 关键边界

- **模型负责局部实现，系统负责流程控制。** 模型不能决定跳过任务、修改验收标准或伪造工具结果。
- **任务声明不等于行为证明。** `finish` 中的 requirement claims 与最终独立 acceptance 分开记录。
- **普通任务不自动跑完整验收。** 普通任务自动构建；局部测试由模型按需要主动执行；完整验收只在最终集成阶段执行。
- **验收输入独立且只读。** 生成工程和测试资产分离，最终结果由宿主侧验证器判定。
- **成功是端到端条件。** 必须任务全部通过、构建通过、必需交互通过、导出完整且报告可发布，单纯编译成功或模型声明完成都不算 run 成功。
