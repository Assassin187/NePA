# NePA P0–P2 实施计划与完成证据要求

日期：2026-09-13。本文是工程实施计划；实际进度和完成审计分别见 `p0-p2-progress.md` 与
`p0-p2-completion-audit.md`。需求来源为 `nepa-next-stage-requirements.md` 第 4–6、10 节，当前权威
架构为 `system_design.md`，历史结果见 `protocol_expansion.md`。不使用 OpenSpec。

## 已接受的实施决策

System Design 11.0 已成为实施权威。Astra Ultra 评审后采用以下简化，它们优先于早期规划草案：

- 保持 Acceptance 1.0；隔离和版本信息属于 Run 7／Report 5，类别来自可信结构化观察，不新增
  public-check CLI。
- 每个模型运行四个与供应商、协议无关的公共工具会话；编译修复必须覆盖跨文件一致性。另运行一次
  使用真实付费模型动作的私有诊断修复，mock 或人工修夹具不能替代。
- 保留原有全部断言和边界，再增加有界随机交互；不对每个时序敏感场景机械重复三次。
- 只投影安全结构化观察和源码诊断；无法分类的服务端原始日志省略，不能假定字符串替换足以消除编码泄漏。
- Qwen 官方能力、账户可用模型和价格已经核实，见 `research/qwen-capability-audit.md`。
- 使用范围化候选摘要，不因无关用户文档变更使候选失效。
- 实施按互不重叠的文件边界分工；共享调用接口在编辑消费者前先约定。

## 1. 范围、授权与基线

用户授权在无需逐项再次确认的情况下完成合理的 P0–P2 设计和实施决策。本轮使用独立 Qwen 人民币
活动：累计 ¥300，每次生成 ¥20／4 小时；探测、失败、恢复和未知调用预留均计入。P3 并行调度、P4
弱模型和 P5 RFC 抽取不属于本计划，生产任务保持单写者串行和已接受 checkpoint。

最终目标仍是 RFC → 经批准的 Spec → Code。保持 Spec 3.0、原始来源、需求文本和覆盖缺口。私有验收
由独立人工资产维护，不得成为模型可见答案，也不由被测生成器自行生成。

不得触碰用户在 `protocol_document/` 的整理、其他已有变更、历史运行和交付归档；不执行推送、合并、
部署、历史清理或原地迁移。

基线事实：

| 领域 | 已确认状态 |
|---|---|
| 历史生成 | `10cb987...` 完成 MQTT／HTTP 可读验收脚本条件下的真实生成，只能作为可行性证据 |
| 覆盖 | MQTT 110 条需求、20 场景、51 条映射／59 缺口；HTTP 27 条、12 场景、26 映射／1 范围缺口 |
| 旧存储风险 | Acceptance、checks 和原始 evidence 曾位于智能体可读目录 |
| 旧验证风险 | 检查器与生成服务曾同容器运行，服务能读取 `/checks` |
| 旧反馈风险 | 原始验证结果和证据引用可能直接进入会话上下文 |
| 旧供应商假设 | 上下文和客户端曾直接依赖 OpenAI-compatible payload，缺少模型能力 profile |
| 可复用基础 | RunStore 预留／结算、活动锁、截止时间、checkpoint、供应商 SSE 和容器沙箱 |

## 2. 合同版本与候选身份

最终实施版本：System Design 11.0、Spec 3.0、Target 1.0、Acceptance 1.0、AgentAction 1.0、Plan 6.0、
Run 7.0、Config 3.0、Report 5.0，以及 `repair-diagnostic/1`。旧提案中的 Acceptance 2.0 和公共检查
manifest 已取消；隔离属于宿主执行属性。

候选摘要必须冻结：生成提交、运行时包和提示词、动作 Schema、配置与模型能力／价格、Spec／Target／
初始 Plan、公共夹具、私有 manifest／脚本／断言映射、随机化策略、验证器／诊断版本、实验驱动、依赖锁
和 Docker 镜像。宿主、内核、编译器和资源限制作为比较条件记录。私有文件摘要只存宿主证据；公共报告
只发布私有套件聚合摘要和验证器版本。

seed、动态端口、请求 ID、时间戳、计费时段和 run ID 每次变化，不属于候选摘要；随机策略的分布、
数量、断言或超时变化则产生新候选。MQTT 与 HTTP 使用不同协议输入摘要，但共享运行时／配置／镜像候选。

第一次可计数 MQTT 前冻结候选，首次成功后封存。运行时、提示词、路由、能力、输入、镜像、价格策略或
oracle 任一变化，都重启三次 MQTT 样本。文档结果提交与生成提交分开，不能追溯改名实验。范围摘要只
覆盖候选文件，无关用户文档不影响运行，也不得为满足整棵工作树干净而被提交、暂存或删除。

## 3. P0：证据移交与基线分析

保留首次 DeepSeek 开发成功和 MQTT／HTTP 扩展运行的原路径、run ID、输入、模型、配置、运行时、任务、
调用、声明、构建、交互、导出复验、费用／未知预留、范围和摘要。混合开发配置必须如实标注。派生报告
写入新路径，不修改原 `run.json`、报告和归档。

统一分析口径：

- 运行创建到终态报告发布的墙钟；生成、最终导出验证和后续独立审计分开计时；中断／离线恢复间隔单列。
- 每任务／会话记录供应商等待、重试退避、上下文准备、命令、构建、私有验证、checkpoint／导出／发布、
  决策、无效动作、读取／重复读取和修复次数。
- 每调用记录任务／会话／决策／尝试 ID、路由原因、请求／返回模型、开始／结束、token 类别、人民币、
  未知预留、失败分类和证据引用。
- 嵌套在 `finish` 中的构建不能重复计时；无法由历史证据还原的时间明确标为不可用或残余，不用 mtime
  虚构精确值。

公共工具夹具和迁移后的 MQTT／HTTP 私有套件在供应商比较前冻结。历史导出复制品通过新私有验证只能
证明验证器回归，不能变成新的私有生成成功。

## 4. P1：存储与访问合同

每个新运行采用以下物理结构：

```text
runs/qwen-e2e/<run-id>/
  run.json                     # 宿主权威状态，模型不可读
  inputs/                      # 仅 spec、target、index 和明确公开资产
  project/                     # 模型唯一可写工程
  agent-evidence/              # 宿主发布的安全视图
  private/acceptance.json
  private/assets/              # 私有 Acceptance 快照
  evidence/                    # 原始调用、动作、验证、性能和导出证据
  checkpoints.git, plans/, interrupted/, export-attempts/
  delivery/, report.json
```

`gold_file/mqtt`、`gold_file/http` 是宿主可信源。源码仓库、历史归档、其他运行和 NePA 自身不得挂载给
智能体。`--acceptance` 始终指向宿主私有最终 manifest。`WorkspaceTools` 的 `inputs/` 只映射公开输入，
逻辑 `evidence/` 只映射 `agent-evidence/`，不映射原始 evidence。

所有文件操作、搜索、摘要刷新、写入、命令、上下文、恢复和导出遵循同一规则：解析 allowlist 根下每个
真实后代路径；拒绝绝对路径、父目录遍历和符号链接逃逸；错误只返回稳定代码和逻辑路径。命令只在沙箱
运行，挂载 `/workspace`、只读 `/inputs` 和可选只读 `/evidence`；禁止 `/checks`、private、原始日志、
父运行目录、Git 对象库、运行时源码、Docker socket 和凭据。模型可见命令结果不含宿主 Docker argv
与绑定路径。原始宿主结果不能重新进入 initial／last feedback、tool 消息、follow-up 或裁剪历史。

导出只取已接受工程和明确公共清单，校验归档成员及符号链接仍在导出根内。禁止打包运行根、私有 manifest、
seed、payload、原始检查、调用和对话。历史可读检查包保持原样并标为 legacy。

## 5. P1：验证与诊断

生成服务和可信检查器必须在两个容器中运行：

| 环境 | 挂载与通信 | 明确排除 |
|---|---|---|
| 编码／构建 | 生成工程、公开输入；无网络 | 私有资产和宿主 evidence |
| 被测服务 | `network=none`；只读 `/workspace` | 检查脚本、payload／seed、宿主运行、共享 PID／IPC |
| 可信检查器 | 独立根／PID／IPC；只读私有资产；加入服务 loopback 网络命名空间 | 生成源码、Docker socket、凭据和宿主网络 |

宿主在启动前记录容器名字／ID，始终尝试清理两者。检查器结果必须是单一、完整、有界结构化对象，且
实际退出码、超时、场景覆盖、服务提前退出、强制关闭和 sanitizer 均进入判定。服务日志和实际交互只存
宿主 evidence。

`repair-diagnostic/1` 只允许传递检查 ID、类别、变体、通过状态、预期／实际结果、类型／长度／顺序、
构建／sanitizer／服务状态，以及经验证存在于公开工程中的源码位置。禁止私有文件名、argv、traceback、
seed、端口、原始向量、完整服务输出和原始 evidence 引用。脱敏是明确字段投影，不是递归字符串替换。

随机化由宿主生成 256 位 seed，并派生每变体、场景的独立端口、ID、载荷、分片和粘包方式；记录实际
收发字节、连接、分块、半关闭、超时和时间戳。同 seed 可重放输入，不保证 OS／TCP 时序完全一致。
保持 MQTT 20／HTTP 12 的原有断言和边界，并在适用场景增加 2–4 次有界变化，不减少覆盖。

离线控制必须证明：所有工具、绝对／符号链接／历史／上下文／导出都读不到私有数据；正确项目通过；
错误响应、只休眠、固定 ID、固定端口、提前退出和真实 sanitizer 项目失败；安全诊断足以让一次真实模型
修复同一私有断言。公共报告与宿主报告严格分开。

## 6. P2：供应商能力、身份与人民币结算

目标模型固定为 `qwen3.7-flash-2026-07-15` 和 `qwen3.7-plus-2026-05-26`。付费前核实北京 endpoint、
精确账户模型 ID、上下文／输出、思考、JSON／工具、usage／cache／reasoning 字段和人民币价格。不得用
近似模型名替代，也不得将未返回身份填成请求模型。

每个模型 profile 明确声明能力与限制。适配器生成一次不可变的实际请求字节，供容量判断、预算预留、
证据保存和发送共同使用。身份缺失／不符、usage 缺失／非法时，不执行动作并保留最坏预留。Qwen 的
缓存 token 归一化，reasoning 已包含于 completion token，不重复收费；阶梯按总输入选择，使用全天价。
只有传输、429 和 5xx 可有界重试，不对请求合同错误回退。

`runs/qwen-e2e` 是唯一 Qwen 活动根，所有探测、夹具、MQTT 和 HTTP 运行在同一原子活动锁下记账。
累计 ¥300，每个生成 ¥20／4 小时；能力和公共工具阶段各 ¥5。没有余额不得发起请求，阶段无法在子限额
内完成则记为不完整，不能静默提高。

通用路由：

| 任务属性／状态 | 模型 | 记录原因 |
|---|---|---|
| 普通 bootstrap／message／requirements 首会话 | Flash | `initial_ordinary_task` |
| shared-wire、integration、follow-up、高影响接口 | Plus | `shared_interface`／`integration`／`followup` |
| 会话失败／耗尽后的重试 | Plus | `task_retry` 与诊断引用 |
| 构建或私有验收修复 | Plus | `build_repair`／`private_acceptance_repair` |

路由只看任务类别和实际失败，不看协议名、消息常量或需求前缀。升级仍使用原任务、会话和决策额度。

公共工具夹具位于 `tests/fixtures/public_tools/`，覆盖发现／读取／写入、精确替换、真实编译失败→读取诊断
→跨文件修复、以及 `finish`／宿主双构建。它们是小型可退出 C 程序，不是协议成品。每个精确模型 ID
独立运行四个夹具，最多 12 次决策；必须完整执行工具、编译、输出和完成合同。无效动作不执行但照常记录。
另以 Plus 完成一次宿主私有错误夹具的安全反馈修复，不能作为协议生成成功。

## 7. 顺序执行门

| 门 | 必须取得的证据 | 未通过时的结论 |
|---|---|---|
| G0 P0 移交 | 原始状态／摘要、任务与调用分析、缺失数据说明，冻结公共／私有检查 | P0 不完整，历史只保留正确暴露标签 |
| G1 设计与合同 | Design 11、Schema／配置／示例及输入→工具→验证→修复→报告链路 | 不能以局部挂载变更声称 P1 完成 |
| G2 隔离回归 | 真实 Docker 控制、MQTT／HTTP 复制导出全套、安全修复和公开归档检查 | P1 不完整，不进入正式 Qwen 协议证明 |
| G3 供应商事实 | 两个精确 ID、Config 3、价格、wire／身份／usage／预算测试 | 未核实或不可用，禁止替换模型 |
| G4 付费能力 | 两个模型的小额真实动作、精确身份和 usage，无隐藏重试／回退 | 记录失败费用，修复通用适配层 |
| G5 公共会话 | 两模型全部公共工具夹具及安全修复边界通过 | 不能从 JSON 探测推断生成就绪 |
| G6 首次 MQTT | 空 checkpoint、纯 Qwen、全任务／声明、双构建、随机私有检查和独立导出复验 | 保留并分类失败，不启动重复样本 |
| G7 MQTT 重复 | 同一候选再完成两个独立空工程成功 | 任一失败或候选改变，都不能作三次稳定性声明 |
| G8 HTTP 跨协议 | 同运行时／配置／路由／镜像完成一个 HTTP 空工程和独立复验 | 只能报告 MQTT，P2 部分完成 |
| G9 最终审计 | 对齐每调用账本、原始／安全证据、摘要、失败分类、需求和变体 | 缺失证据保持不完整 |

失败分类至少区分：供应商可用性／认证／限流／网络；能力或 wire 适配；动作语法／Schema／声明；上下文
容量／过期；任务设计／路由；生成代码构建／接口／语义；验证器／oracle／基础设施；sanitizer／运行时；
预算／截止／中断。每次失败保留输入、调用、动作、检查引用、实际原因和修复提交。只能通过记录的新候选
修改生产代码／配置／输入；不得人工修生成代码、导入旧方案、关闭检查或按需求 ID 定制语义。

Qwen 成功要求所有生成和修复调用都由 Qwen 完成；使用其他供应商的运行须标为 mixed-model 并排除。
禁止客户端响应缓存和历史工程复用；供应商 prompt cache 折扣可以按官方 usage 记账，但不等于缓存答案。

## 9. 实施边界与验证

实施按以下责任边界拆分：主集成负责设计、P0 清单、orchestrator／application／CLI 和 RunStore 最终集成；
隔离验证负责 sandbox／verification／worker／workspace；验收报告负责 gold Acceptance、report、Schema／
lint；供应商记账负责 config、client、OpenAI-compatible、telemetry；会话上下文负责 session、context 和
coder prompt；实验验证负责既有测试、公共夹具和 P2 分阶段驱动。共享模块不得由多个写者同时编辑。

离线验证至少包括：

```bash
python -m pytest -m 'not live_e2e'
python -m ruff check nepa tests
python -m mypy nepa
python -m build
```

容器测试必须真实执行，Docker 不可用导致跳过时 G2 仍不完整。还须检查 wheel 安装后的行为、CLI lint／
run／status／resume／版本拒绝、归档内容和复制导出 clean 构建。离线阶段禁止付费开关；随后只能按 G4–G8
实验驱动和已采用预算执行。任何模型不可用、价格未核实、预算耗尽或运行失败都保留证据并标明对应门
未完成，不能因单元测试通过而改称 P2 完成。
