# MQTT 运行耗时分析

## 1. 分析对象与结论

本报告分析 MQTT 最近一次成功 NePA 运行：

```text
runs/baseline-10cb-mqtt/20260914T151904Z-94aeaf27
```

运行包含 23 个任务、839 次 LLM 调用、29 个 session，最终 release 和 san
版本的全部验收场景通过。

核心结论是：MQTT 运行时间主要消耗在模型 API 等待和后续模型迭代，而不是
编译、测试进程或最终 acceptance。端到端耗时约 87 分 30 秒，其中约 78 分钟
是 LLM API 时间。

本报告只描述运行证据，不改变 `project_docs/system_design.md` 的设计语义。

## 2. 计时口径

数据来源为运行目录中的 `run.json`、`report.json`、`evidence/calls`、
`evidence/actions` 和最终导出证据：

- LLM 时间使用每个 `evidence/calls/*.response.json` 中的 `elapsed_s`；
- 模型主动执行的命令使用 action 结果中的 `duration_ms`；
- 最终自动构建和 acceptance 使用 `evidence/exports/*.json` 中的执行时间；
- 端到端时间使用 `run.json.created_at` 到 `report.json` 生成时间的差值。

端到端时间不是运行时显式记录的单一字段，因此应理解为本地证据时间戳得到的
近似值。API 时间包含供应商处理和网络等待，现有证据不能继续拆分二者。

参考文件：

- `runs/baseline-10cb-mqtt/20260914T151904Z-94aeaf27/run.json`
- `runs/baseline-10cb-mqtt/20260914T151904Z-94aeaf27/report.json`
- `runs/baseline-10cb-mqtt/20260914T151904Z-94aeaf27/evidence/exports/fca5eda879204d5eac5c36d278f97e54.json`

## 3. 端到端时间分布

| 时间部分 | 耗时 | 占端到端时间 |
|---|---:|---:|
| 839 次 LLM API 调用 | 4,679.5 秒（77 分 59.5 秒） | 89.1% |
| 模型主动执行的 `run_command` | 414.1 秒（6 分 54.1 秒） | 7.9% |
| 最终自动 clean/build/acceptance | 48.3 秒 | 0.9% |
| 未单独计时的编排、文件操作、任务切换和报告发布 | 约 108.0 秒 | 2.1% |
| **合计** | **约 5,249.9 秒（87 分 29.9 秒）** | **100%** |

839 次调用的首个请求到最后一个响应结束之间是 5,152.8 秒。最后一个 LLM
响应之后，最终自动检查和报告发布又消耗约 97.0 秒，其中最终 clean/build/
acceptance 的明确计时是 48.3 秒。

action 目录共记录 632 个 action，其中 235 个是实际执行的
`run_command`。普通任务提交后的自动 build gate 没有单独的 action 计时，
因此被包含在任务跨度或未单独计时部分中。

## 4. 按任务的主要耗时

下表按每个任务首个调用到最后一个调用结束的墙钟跨度统计；百分比以整个
端到端运行时间为分母。任务跨度包含该任务内部的模型调用、已记录命令以及
调用之间的等待。

| 任务 | 调用数 | session 数 | 任务跨度 | 占总时间 |
|---|---:|---:|---:|---:|
| `requirements:007` | 81 | 3 | 16 分 36 秒 | 19.0% |
| `requirements:003` | 46 | 2 | 11 分 18 秒 | 12.9% |
| `requirements:002` | 40 | 1 | 7 分 37 秒 | 8.7% |
| `shared-wire` | 21 | 1 | 7 分 24 秒 | 8.5% |
| `message:connect` | 46 | 2 | 6 分 02 秒 | 6.9% |

前五项合计约 49 分钟，占端到端时间约 56%。其中：

- 十个 `requirements` 任务合计消耗 2,947.9 秒 API 时间，占 API 时间
  63.0%；
- 十个 `message` 任务合计消耗 1,177.1 秒，占 25.2%；
- `shared-wire` 单独消耗 439.6 秒，占 9.4%。

### 4.1 `requirements:007` 是最大热点

该任务经历了三段 session：

| session | 模型 | 调用数 | API 时间 |
|---:|---|---:|---:|
| 1 | `deepseek-flash` | 40 | 295.1 秒 |
| 2 | `deepseek-v4-pro` | 40 | 626.4 秒 |
| 3 | `deepseek-v4-pro` | 1 | 13.1 秒 |

该任务共 81 次调用，约 15 分 35 秒 API 时间，另有命令和调用间隙后形成
约 16 分 36 秒任务跨度。

整个运行相对于每个任务的首个 session 多出 6 个 continuation session，
这些 session 共包含 56 次调用、995.5 秒 API 时间。这个数字表示 continuation
阶段的工作时间，不应全部视为纯切换开销；session 切换间隙本身合计约 18.4 秒。

## 5. 模型路由与不可执行输出

### 5.1 Pro 调用的时间占比高

| 模型 | 调用数 | 调用占比 | API 时间 | API 时间占比 | 平均每次 |
|---|---:|---:|---:|---:|---:|
| `deepseek-flash` | 749 | 89.3% | 3,197.5 秒 | 68.3% | 4.27 秒 |
| `deepseek-v4-pro` | 90 | 10.7% | 1,482.0 秒 | 31.7% | 16.47 秒 |

Pro 只占约 10.7% 的调用，却占 31.7% 的 API 时间。`shared-wire` 的 21 次
调用全部使用 Pro；`requirements:007` 和 `requirements:003` 的 continuation
也明显增加了 Pro 等待时间。

### 5.2 未形成可执行 action 的响应

按响应中是否形成允许的工具 action 统计，839 次调用中有 189 次没有形成
可执行 action，占 22.5%，消耗 690.1 秒 API 时间，占端到端时间约 13.1%。

这 189 次包括：

- 164 次解析结果没有有效 `tool`；
- 19 次没有得到可解析的 action 对象；
- 6 次解析结果是列表而不是 action 对象。

其中 185 次来自 Flash，4 次来自 Pro。最长的一次是调用 000677：输出达到
长度上限，耗时 64.4 秒，但没有产生可执行 action。另有若干响应使用 DSML
包裹、只输出代码或只输出工具参数，导致宿主机无法执行。

这部分是最明确的可优化时间来源，但它与复杂任务、Pro 路由和 continuation
阶段存在重叠，不能与这些项目简单相加。

## 6. 测试、构建和 acceptance 的耗时

### 6.1 模型主动测试

235 个有记录的 `run_command` 合计 414.1 秒。最长的几次测试命令如下：

| 任务 | 命令耗时 |
|---|---:|
| `requirements:006` 全行为场景测试 | 26.8 秒 |
| `requirements:008` 全行为场景测试 | 22.6 秒 |
| `final-integration` 全行为场景测试 | 22.1 秒 |
| `requirements:007` Keep Alive/会话测试 | 17.2 秒 |
| `requirements:007` Keep Alive/会话复测 | 16.8 秒 |

上述五次合计 105.5 秒，占模型主动命令时间的 25.5%，但只占端到端运行
时间约 2.0%。

开发阶段共有 8 次非零命令结果，命令自身合计耗时约 13.0 秒。最初的
`tests/run_behavior.sh` action 耗时 7.8 秒，其中 `pubsub`、
`length_boundaries` 和 `coalesced` 超时。超时之后的主要成本是模型继续
分析和修复，而不是测试进程本身运行很久。

### 6.2 最终自动验收

最终导出证据中的自动时间为：

| 项目 | 耗时 |
|---|---:|
| `make clean` | 0.315 秒 |
| `make release` | 1.368 秒 |
| `make san` | 2.319 秒 |
| release 验收（20 个场景） | 22.206 秒 |
| san 验收（20 个场景） | 22.103 秒 |
| **合计** | **48.311 秒** |

最终 acceptance 本身的 44.309 秒中，主要时间来自测试脚本中有意设置的
等待：

- `keep_alive`：Keep Alive=2，服务端按 1.5 倍周期等待约 3 秒断开；
- `keep_alive_zero`：脚本显式等待 4 秒确认连接不应因 Keep Alive 断开；
- `keep_alive_activity`：连续 5 次各等待 1 秒，再等待约 3 秒确认断开。

三个场景每个版本约贡献 15 秒，两版本约 30 秒。这是验收语义要求的固定
等待，约占最终 acceptance 时间的三分之二，但只占整个运行时间约 0.6%。

`verification_worker.py` 按顺序执行每个 check，但当前证据只记录整个 worker
的耗时，没有记录单个 check 的实际耗时。因此上述单场景时间是由测试源码和
服务端 Keep Alive 逻辑推导出的近似下界，不是 worker 输出中的独立计时值。

## 7. 与 HTTP 运行对比

| 指标 | MQTT | HTTP |
|---|---:|---:|
| 端到端耗时 | 87 分 29.9 秒 | 22 分 27.3 秒 |
| LLM API 时间 | 77 分 59.5 秒 | 18 分 35.4 秒 |
| LLM 调用数 | 839 | 225 |
| 有记录的命令执行时间 | 6 分 54.1 秒 | 3 分 14.9 秒 |
| 最终自动 gate | 48.3 秒 | 9.6 秒 |

MQTT 比 HTTP 多约 65 分钟，其中约 59 分 24 秒来自 LLM API 时间。MQTT 的
命令执行时间只多约 3 分 39 秒，最终 gate 只多约 39 秒。因此 MQTT 的长耗时
主要来自任务数量、需求数量、跨模块联动、额外 session、模型路由和不可执行
输出，而不是 acceptance 测试或编译。

## 8. 结论与后续优化优先级

按当前证据，优化优先级应为：

1. 降低没有形成可执行 action 的响应比例，尤其是 DSML/非 JSON action 输出；
2. 减少复杂任务中的重复读取、重复推理和 continuation 工作；
3. 检查 Pro 路由和复杂任务上下文组织，重点关注 `shared-wire`、
   `requirements:003` 和 `requirements:007`；
4. 保留当前 acceptance 语义，不应为了减少几十秒而删除 Keep Alive 等
   必要等待或降低最终验收强度。

这份分析不对上述优化做因果保证：API 时间、任务复杂度、模型路由和响应格式
错误在本次运行中相互影响，现有单次 MQTT 运行只能确定耗时分布，不能提供
受控 A/B 加速结果。
